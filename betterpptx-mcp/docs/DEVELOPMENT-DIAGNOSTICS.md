# Private development diagnostics

Set `BETTERPPTX_DIAGNOSTIC_TRACE=1` in the private deployment environment and restart the MCP process. Leave `BETTERPPTX_LOG_PAYLOADS` and `BETTERPPTX_LOG_SECRETS` unset. The diagnostic trace is independent of the general logger and is disabled by default.

The trace writes private NDJSON under `logs/betterpptx-mcp/diagnostic` (or `BETTERPPTX_DIAGNOSTIC_TRACE_DIR`). It records: request correlation IDs, MCP transport, tool names, read-only/write annotation counts, per-tool input-schema byte counts and SHA-256, public build/schema identity, call outcome/error code/duration, internal tool start/end/throw spans, HTTP status/response bytes, and authentication decision class. It never records request arguments, response bodies, slide content, personal identity, raw client metadata, tokens, URLs, or credentials. Each process file rotates at 8 MiB with three retained rotations; matching files older than seven days are removed on the next trace initialization. Restrict filesystem access to the operator account. Do not publish trace files.

When the existing general development logger is independently enabled, its narration, billing, deck-state and save events inherit the same request ID. That logger has separate payload/secret switches; do not enable them on a public endpoint. The private diagnostic trace remains allowlisted even if other logging settings change.

Use `tools.list` evidence to distinguish what the server sent from what a particular host made callable. The server cannot observe a host's internal tool filtering or cached projection. Compare the trace's names and counts with the actual client-visible function definitions. A browser model saying “Found N tools” is not proof of a fresh MCP `tools/list` call. In this development case, the raw public MCP returned 53 actions (38 read-only, 15 write-capable), and the ChatGPT plugin management page displayed the write definitions. Yet two tested Chat-mode conversations received only the same 38 read-only callable actions. A fresh chat did not cause a fresh server `tools/list` request, so the exact host filtering/cache policy remains unobserved. This is not a reason to mark write actions read-only or bypass authorization.

Diagnostics are not a public MCP feature. There is no trace retrieval tool or route. `/log-viewer` remains loopback-only and does not serve these files. Disable the switch after investigation; keep only the minimum necessary evidence for a specific incident.
